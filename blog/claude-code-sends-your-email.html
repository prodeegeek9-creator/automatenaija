Claude Code sends your email? Reproduce and fix

Reproduce the leak in minutes, apply prompt and network mitigations, and verify logs so Claude Code stops sending your email to external sites.

By the Automate Naija team·6 November 2026·6 min read

If claude code sends your email to external websites, stop using the prompt or workspace immediately, reproduce the behaviour safely, then apply client side redaction, network blocking and temporary address workarounds. This guide shows how to reproduce the leak in minutes and gives immediate mitigations you can use today.

claude code sends your email: reproduce in minutes

Reproducing the issue quickly gives you evidence to act and to report. Use a test address that you control, for example test@example.com, not a personal or company email. Open Claude Code in your browser, open Developer Tools, switch to the Network tab, then paste a short prompt referencing the test address. Watch for any outgoing HTTP requests to third party domains that include the email in the URL, query string or request body.

Example quick test prompt to paste in Claude Code
"Here is an email to include in the output: test@example.com. Do not share this externally, just echo the email back in plain text."

If you see requests that contain the test address, capture them with the browser Network tab or with a proxy such as mitmproxy or a packet capture like tcpdump or Wireshark. Save the capture and timestamp. The Hacker News discussions reporting this behaviour help confirm community reports, see the thread reporting addresses sent to websites and the SEO thread for context.

Why this happens

There are a few likely causes to the behaviour people see. First, prompt content that includes an address may be used by internal logging, telemetry, or by auxiliary tooling that performs lookups. Second, some assistant features attempt to fetch or validate external content, and those subsystems can forward user-provided strings to third party services if not correctly sandboxed. Finally, browser extensions or third party integrations can intercept page content and leak it externally. You should assume any string pasted in a prompt can be forwarded unless you can verify otherwise.

Immediate mitigations, step by step

  1. Stop using the affected session, and sign out. If you paste sensitive data into Claude Code, close the tab to stop further immediate interaction.
  2. Reproduce with a test address as above and capture network evidence. Use Developer Tools Network, or run mitmproxy, or capture packets with sudo tcpdump -i any -w claude-leak.pcap while reproducing.
  3. Sanitise prompts before sending. Replace real addresses with placeholders using a small client side script, browser extension or clipboard tool. For example replace name@company.com with [EMAIL_REDACTED] before paste.
  4. Use temporary email addresses when testing, such as Mailinator or 10 Minute Mail, so any leak does not expose real inboxes. Do not use production or staff emails in prompts.
  5. Block outbound network requests to unexpected domains. On macOS or Linux add temporary /etc/hosts entries or use a network firewall to block the domain you observed, or use an enterprise proxy to deny unknown hosts. On Windows use Windows Defender Firewall outbound rules.
  6. Turn off or audit browser extensions. Disable extensions that can read page content, such as SEO toolbars, clipboard managers, or injection scripts, then retest.
  7. Rotate any exposed credentials. If the leaked string included API keys, account tokens or internal emails, rotate them immediately and revoke sessions as needed.

Tool specific notes: n8n, Make.com and Zapier

These platforms often send prompt text to LLMs or store logs. Apply the following platform specific steps.

n8n

In n8n, avoid embedding raw personal data into nodes that log or forward it. Use the Code node to perform client side redaction before calls, and the HTTP Request node only after you have replaced or hashed sensitive fields. For example, in a prior node set an expression that replaces emails, then feed the sanitized field into the HTTP Request node. Also check workflow execution logs in the n8n UI to see any stored values.

If you run self hosted n8n, place an egress rule on your server or a reverse proxy to block unexpected outgoing hosts. See our related post on common n8n troubleshooting for guidance about workflow failures.

Make.com

In Make.com, sanitize variables in a prior module step before an LLM or HTTP module. Use the parse and replace functions available in text modules to remove email patterns. Review scenario execution history for saved bundles that may include the original text and delete any containing sensitive strings.

Zapier

In Zapier, add a Formatter step before any integration that could forward text, using the Formatter by Zapier action to replace or mask emails. Check Task History for tasks that include the original data and delete tasks if needed. Also rotate any connected account keys if you see suspicious calls.

How to stop it happening again, a verification checklist

  • Audit all prompts, templates and stored messages. Replace real addresses with tokens in source templates and environment variables.
  • Enable strict logging retention and redact logs where possible. If your platform supports automatic redaction, turn it on.
  • Run regular network captures for a short window after deployments or when testing new automations. Use tcpdump or your corporate packet capture and search for email patterns with grep or Wireshark filters like http.request or frame contains "@".
  • Implement blocking rules for unknown outbound domains at the perimeter, and require allow lists for automation servers.
  • Use organization controls where available. If Claude or your provider offers team or org settings for telemetry or data sharing, disable optional data sharing, and require admins to approve integrations.
  • Train your team and contractors, and add a short SOP so anyone embedding prompts follows the redaction workflow and uses temporary addresses for tests.

When to get help

If you see confirmed requests that contain real user or customer emails, or if you can reproducibly show personal data going to third party domains, escalate. Contact the service provider support and include your captures, timestamps and the exact prompt used. If the leak touches customer data or regulatory personal data, involve your security team and consider notification obligations under local law.

If you need help instrumenting network captures or removing sensitive items from logs, seek an experienced developer or security consultant. For immediate community discussion and reports, see the Hacker News threads linked above.

Frequently asked questions

How quickly can I tell if Claude Code leaked an email from my prompt?

You can confirm a leak in minutes by using a test email such as test@example.com, opening your browser Developer Tools Network tab or running mitmproxy, submitting the prompt, and watching for outgoing requests that include the test address. Save the capture and timestamp as evidence.

What is the fastest mitigation if my real email was pasted into a prompt?

Stop using the session, sign out, disable any suspicious browser extensions, replace the exposed address with a new one or a token in templates, and use a temporary email for tests. If credentials leaked, rotate them immediately and check access logs for suspicious activity.

Can I block Claude Code from contacting external sites from my network?

Yes, block outbound requests at your gateway or host firewall, add temporary /etc/hosts entries to redirect suspicious hosts, or use a proxy with an allow list. For cloud or managed services, request tighter egress controls from your IT team.

Should I report the issue to the provider and what details will they need?

Report it, include reproduction steps, the exact prompt you used (or a sanitized version), timestamps, and network captures showing the outbound request. If customer data was involved, include scope and affected user counts so the provider can prioritise a response.
