Make.com outreach automation debug checklist

A practical checklist to debug Make.com outreach funnels that fail silently between webhook, Iterator and CRM modules.

By the Automate Naija team·20 October 2026·7 min read

When your outreach funnel in Make.com will not trigger or fails silently, start with a focused make com outreach automation debug checklist: verify the Custom Webhook URL and scenario is active, send a simple test payload, inspect the scenario execution history, check the Iterator input is an array, and add filters to prevent empty mapping into CRM.

Why Make.com outreach automation debug is needed

Silent failures happen when data never reaches the part of the scenario that logs errors. Common blind spots are inactive scenarios, uninitialized webhooks, format mismatch for the Iterator module, or downstream CRM modules skipping or rejecting empty fields. You need a repeatable process to surface the actual error so you can fix it quickly.

Step by step fix (copy these tests and checks)

  1. Confirm scenario is active and webhook initialized. Open the scenario, make sure it is marked Active. Open the Custom Webhook module, then click the webhook to copy the URL again. If you edit the scenario after creating a webhook, always re-copy and re-register the URL where needed.
  2. Send a minimal test request. Use curl or Postman to remove client variables. A simple POST with JSON is best. Copy and run: 
    curl -X POST 'https://hook.make.com/your-webhook-id' -H 'Content-Type: application/json' -d '{"email":"test@example.com","items":[{"id":1}]}'
    If you expect GET, send GET. If the request fails, check network, proxy, or URL errors first.
  3. Inspect Execution history and run details. Open the scenario, find Execution history or Scenario Runs. Look for the latest run created by your test request. Expand module logs to see incoming payload, status codes and any module-level error text. If there is no run, the webhook did not reach Make.
  4. Fix the webhook not firing. If there is no run: verify URL, method, and Content-Type. Confirm the external sender is not blocked by a firewall or incorrect DNS. If you use a custom domain or proxy, test direct to the Make webhook URL. Also check that you are not hitting a cached or old URL in your outreach tool.
  5. Validate the Iterator input. The Iterator module requires an array. If you see errors like an iterator complaint or no iterations, inspect the incoming JSON path you map. Use a Set or JSON module to normalise the field into an array before Iterator. Example, if your payload has items but sometimes it is a single object, wrap it like this in a Set step: map items to an array containing the item when not already an array.
  6. Prevent empty mapping into CRM. Add a Filter between the value source and the CRM module to block runs where required fields like email are empty. In the Filter, use the condition email is not empty. This prevents silent successes where the CRM returns 200 but ignores empty fields.
  7. Re-run and watch module logs. After changes, run the same curl test and watch each module input and output. Look for HTTP 4xx or 5xx responses in HTTP/CRM modules and correct payload or authentication issues.

Common silent-failure causes and quick fixes

  • No scenario run created, cause: inactive scenario, wrong webhook. Fix: activate scenario, re-copy webhook, test again.
  • Make com webhook not firing, cause: wrong method or Content-Type. Fix: match the method and add Content-Type: application/json when sending JSON.
  • Iterator module error, cause: not an array. Fix: add a Set or JSON normalisation step, or change mapping to the correct array path like items instead of item.
  • CRM module accepts but data not present, cause: empty fields or wrong key names. Fix: add Filters to prevent empty mapping, confirm field keys match CRM API names.
  • Silent retry or ignored errors, cause: module configured to continue on error or a custom error handler that swallows errors. Fix: check module settings and remove any error-handling routes that hide failures.

Test scenarios you can copy

Run these tests from a terminal or Postman to reproduce common problems quickly.

  • Basic webhook POST 
    curl -X POST 'https://hook.make.com/your-webhook-id' -H 'Content-Type: application/json' -d '{"email":"test@example.com","items":[{"id":1}]}'
  • Missing field test to check Filters 
    curl -X POST 'https://hook.make.com/your-webhook-id' -H 'Content-Type: application/json' -d '{"items":[]}'
    This shows whether your Filter blocks the run before the CRM module.
  • Single item vs array test for Iterator 
    curl -X POST 'https://hook.make.com/your-webhook-id' -H 'Content-Type: application/json' -d '{"items":{"id":1}}'
    If Iterator fails here, you need to normalise items into an array.

Tool-specific notes (Make.com, n8n, Zapier)

Make.com: use Custom Webhook, Iterator, Set, Filters and Execution history. Activate scenarios and re-copy webhook URLs when you edit them. For preventing empty mappings, add a Filter with condition field is not empty before CRM modules. See community threads like Need Make.com Expert to Debug & Launch Existing Outreach Automation and Preventing an empty field being mapped for real reports and fixes.

n8n: similar issues appear with webhooks and iterators. n8n calls custom code nodes Code and HTTP calls HTTP Request. If you move between n8n and Make.com, remember node names and error views differ. For alerts on failures in n8n, see our post on n8n alert when workflow fails.

Zapier: Zaps and steps use triggers and actions that also silence errors when fields are empty. Use paths and filters to stop empty records from passing into CRMs.

How to stop it happening again

  • Add a staging webhook URL and a single test scenario to validate every payload format before pushing to production.
  • Use Set modules to normalise input shapes. Always make arrays explicit before using Iterator.
  • Place Filters that enforce required fields such as email or phone and log filtered out records to a debug sheet or Slack channel.
  • Enable clear logging and alerting, either via built in Execution history or a notification step that triggers on module error.

Quick checklist to hand a freelancer

  1. Open scenario, confirm Active, copy webhook URL and paste a working curl test result.
  2. Provide a screenshot of Execution history showing the last run and module inputs/outputs.
  3. Show Iterator input path and confirm it maps to an array in at least one successful run.
  4. Add Filters for required CRM fields and show a test where missing fields are filtered out.
  5. Deliver a short report listing any API 4xx/5xx responses and suggested payload fixes.

When to get help

If your webhook receives no runs after verifying URL and network, or if a CRM returns opaque 200 responses without creating records, get help. Share Execution history snapshots and the raw request you used to test. Community threads often help, for example the Make.com forum question requesting an expert to debug [link above]. If you need regular support, hire someone who will add alerting, staging tests and robust Filters so the funnel fails loud, not silent.

Frequently asked questions

Why does my Make webhook not fire when I send requests?

Common causes are the scenario is not Active, you copied an old webhook URL, the HTTP method or Content-Type does not match what the webhook expects, or the request is blocked by a firewall or proxy. Re-copy the Custom Webhook URL, activate the scenario, and test with a simple curl POST including Content-Type: application/json.

How do I fix an Iterator module error in Make.com?

The Iterator expects an array. If your incoming payload sometimes includes a single object, normalise it first using a Set module or JSON step so the field is always an array. Test with both an array and a single-item payload to confirm the Iterator runs the expected times.

What stops my CRM from getting data even though Make shows success?

CRMs often ignore empty required fields or silently discard records if keys do not match. Add a Filter before the CRM to ensure required fields like email are not empty. Inspect the module output for the exact keys you mapped and compare them to the CRM API field names.

How can I prevent empty values being mapped and causing silent failures?

Use a Filter or conditional check before the mapping to the CRM. In the Filter, require email or another key to be not empty. Alternatively, add a Set step to construct only the keys that have values so you do not send empty fields to the CRM.
